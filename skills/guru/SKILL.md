# Guru

Take one piece of work (a run) from request to a PR ready for the owner's merge, with this whole prompt as the method: one goal, a hard done bar, and the bottega skills as building blocks instead of phases to walk. It runs from Claude Code, on the harness's dynamic workflows, loops, and subagents. Every dispatch names the model and effort from its worker's row of [the worker table](../maestro/references/workers.md), and every GPT dispatch runs per [the codex dispatch method](../maestro/references/codex-dispatch.md).

Ultracode: orchestrate the whole run as dynamic workflows, not just the build. Fan out wherever work is genuinely independent: discovery sweeps, builders per slice, critics, verifiers per finding, QA per scenario. Keep every judgment call in your own turns: the design, the verification of findings, the acceptance of the head. One measured warning: parallel workers on one coupled concern break each other's assumptions and make it worse; anything coupled gets a single owner working sequentially.

Write your session id to `.bottega/discovery` before the first dispatch, so the route guard reads every dispatch from that moment. The run never merges, approves, or auto-merges the PR: the owner's merge is the release. Don't stop to ask permission; every decision made on the user's behalf goes in the PR body, the one most likely to draw a different answer first.

Before any code, use `bottega:discover` to find what the user couldn't say, its explore sweeps fanned out in one dynamic workflow: the blind spot pass for their unknown unknowns, interviews one question at a time with your recommended answer so a reply is a yes or a correction, rendered prototypes for anything they'd only recognize by seeing, source code references for behavior nobody can put into words. Then use `bottega:open` to claim and isolate the run.

Scale the machinery to what discovery left open, never to the diff's size. Each move below exists to settle open decisions, so make it only while decisions remain and weigh it by the cost of being wrong: no open design questions means a contract of a few lines and its tests, no panel, no cold read; one decision that is open, costly to reverse, and settled by no cheap spike goes to `bottega:panel`, and you synthesize. A diff statable in one sentence goes straight to build and review. Whatever the size, four things never scale down: the worktree, the gates green, the cross-company review of the integrated diff, and the PR.

Write the run contract: one working file on the branch, written for the workers, not for posterity. It carries the settled decisions, the slice map with each worker's owned files, the interfaces between slices, and the quality bar the critics score against. Turn every acceptance criterion that can be a test into a failing test now: the tests carry the agreement, and a failing test turns green through code, never through editing the test. A bar no existing gate checks gets a small reproducible check built first. When the contract fixes decisions worth attacking, one cold read before building: a fresh read-only dispatch on the plan editor's row, given only the contract, the tests, and the repository, returning it approved or rewritten whole; take what survives your own judgment. Keep the contract live: when the code moves it moves in the same commit, and every deviation lands in it with its reason; a stale contract is worse than none, because workers execute it confidently. The contract never merges. By close its content has become the tests, the PR body, and, only where the repository keeps decision records, one record for what the code cannot explain by itself.

Use `bottega:build` to deliver the contract's slices, handing the workers the contract wherever its method reads the plan and the spec; builders work on the builder's row under `bottega:implementing`, and renames, doc sync, and other mechanical chores go to the mechanic's row. A builder proving its brief wrong with evidence is a result, not a failure: choose the cautious option, log the deviation in the contract, and let it continue.

/loop the review until nothing blocking survives a full round. Each round, two harsh critics read the integrated diff cold: one on the Claude critic's row and one on the GPT critic's row, isolated from the builders and from each other, never shown the contract, judging the code against the repository's own standards and the contract's quality bar; when the work has a visible reference (a pointed-at implementation, a rendered design), each puts the result beside it, blind, and says which is better and why. Separately each round, one fresh dispatch on the conformance checker's row compares the diff against the contract and the tests, reporting what is missing, what nobody asked for, and what looks wrong, quoting the contract line each finding rests on; neither pass sees the other's findings. Adversarially verify every finding yourself before accepting it. Accepted blockers (correctness, security, data safety, a broken public interface) go to fresh builders per `bottega:build` and the loop reruns at the new head; real findings below that bar become followup issues, filed before the PR opens.

Then QA: a fresh worker on the QA driver's row that saw none of the work drives every changed scenario per `bottega:qa`. Read each failure before dispatching anything: not every FAIL is a code defect, and a failure that traces to a decision in the contract goes back to the contract, never to a builder patching the symptom. Every product fix re-enters the review loop. Publish the evidence per [the evidence method](../close/references/qa-evidence.md).

Close: for every decision and criterion in the contract, point at the evidence that proves it, a test, a command output, a QA verdict; unproven means not done. Open the PR for a reader who was not in the run: what changed and why, the decisions made on the user's behalf, the deviations log, both critics' and the conformance check's verdicts, and the QA evidence. /loop on the checks as tracked background Bash until every one is green and the merge state clean, routing anything a code change can fix back through build, review, and QA. Then report the PR ready and stop; anything only a person can clear, name it to the user and leave the PR open.
