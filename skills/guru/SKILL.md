# Guru

Take this to a green PR ready to land: `$ARGUMENTS`. The diff should be good enough that a reviewer who wasn't in the run would merge it without asking for a change. When my words don't say how the PR lands, ask me once before any other work: land on green, or hold for you. Then use `bottega:open`, which isolates the run in its own worktree and branch, enters it, and records the owner and the release answer; the whole run works from inside that worktree. Claude workers run on Opus, codex ones on gpt-5.6-sol per [the codex dispatch method](../maestro/references/codex-dispatch.md).

Ground yourself in the repo before anything else: read its agent map (`AGENTS.md` or `CLAUDE.md`) for its commands and gotchas, its `CONTEXT.md` for the domain terms where one exists, and its `docs/lessons` and `docs/adr` before deciding anything they already decided. Speak the repo's language in briefs and code, and talk to me like one human to another: simple, concise, no jargon, what happened rather than a label for it. Invent no vocabulary of your own. Then sweep outward before you settle anything: fan out cheap workers, Opus at low effort or codex with web search on, to find how others already solved this and to read what the installed versions actually do, from their own docs and source rather than from memory.

Before any code, find what I couldn't tell you. Do a blind spot pass for my unknown unknowns. Interview me one question at a time, in plain words, architecture-changing questions first, each with your recommended answer so I can just say yes or correct you. Anything I'd only recognize by seeing, build wildly different directions and let me react to the rendering. For behavior I can't put into words, take the implementation I point at and reimplement its semantics.

The design is yours and made before building: the domain model in the repo's own terms, deep modules behind simple interfaces, clear ownership and boundaries, behavior living where its data lives. Keep the agreement in a run contract on the branch, not in committed spec or plan files, scaled by what's unknown and what's costly to reverse, never by diff size: my most-likely-to-change decisions first, then the slices, each with its owned files and specced by the richest artifact that exists, the implementation to port, the render I approved, a failing test where one pins a criterion. A costly open decision goes to `bottega:panel`; you synthesize. One cold read of the contract by codex before building, returned approved unchanged or rewritten whole, the rewrite its only way to object. The contract moves in the same commits as the code; delete it before the PR opens, once the PR body carries its decisions.

Fan out subagents and ultracode: one builder per slice, coupled work under a single owner, a big slice free to fan out subagents of its own. Brief each builder with the goal, the fixed design, the domain terms, the exact files and references, the gate commands, and this doctrine: follow the technology skills installed in this runtime and the current documentation for the installed version, and take the standard way first; work test-first, watch the test fail, and test behavior through public interfaces, never internals; reuse before you build, the codebase's own helper first, then the standard library, then an installed dependency, and a new dependency is a question, not a decision; mock only at real system boundaries; repair at the cause, reproduced as a failing test and fixed in the shared path, not the named symptom; do the simplest thing that works well, and aim YAGNI at speculative structure, never at product quality, because validation, data safety, security, accessibility, and honest errors are the product; update the docs the slice touches inside the slice; match the surrounding code and say each thing once. A builder that finds the brief's premise wrong takes the conservative better call and reports it with evidence; it asks only when the answer would cross its slice. Gates green at every integrate; reports are claims until verified.

Every user-facing slice gets a harsh drive through the real interface before it merges, with license to roam past the changed scenarios and batch-report everything real it finds, pre-existing defects included. A failure caused by a wrong decision changes the decision in the contract and rebuilds; a repair is done only when the re-drive confirms it. The terminal pass is a thin sweep, evidence per verdict.

When everything has landed, /loop the review until a full round finds nothing blocking: two really harsh critics read the whole integrated diff cold, one Opus and one codex, given the diff, the repo, and the quality bar, never the contract, each reporting what it verified sound alongside its findings; where there's a visible reference, compare the result to it side by side, blind, and say which is better. One codex read checks the diff against the contract and the tests. Check each finding is real before you fix it; when the critics contradict each other, arbitrate with reasons. Blockers go back to builders and the round reruns; the rest become followup issues.

Then use `bottega:close`, which files the followups, opens the PR for a reader who wasn't in the run, arms the repo's own auto-merge, watches the checks, and ends with the PR merged, ready, held for me, or waiting on what only a person can clear. A red its watch finds that a code change clears goes back to a builder and re-enters the review round.
