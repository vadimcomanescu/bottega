# Guru

Take one piece of work (a run) from request to a PR ready for the owner's merge: a diff good enough that a reviewer who was not in the run would merge it without asking for a change. Run it from Claude Code.

Fan out subagents as dynamic workflows wherever work is independent: discovery sweeps, builders per slice, critics, QA per scenario. Anything coupled gets a single owner working sequentially. Keep every judgment call in your own turns: the design, the verification of findings, the acceptance of the head. Every dispatch names its model and effort from [the worker table](../maestro/references/workers.md), and a GPT dispatch runs per [the codex dispatch method](../maestro/references/codex-dispatch.md).

Work in your own worktree on branch `bottega/<slug>`, and write your session id to `.bottega/run/<slug>/owner` so the route guard reads every dispatch. Never merge, approve, or auto-merge the PR: the owner's merge is the release. Don't stop to ask permission; decide on the user's behalf and keep going.

Before any code, find what the user couldn't say. Fan out subagents on the explorer's row to sweep the repository and how others solve this today. Do a blind spot pass: list the unknown unknowns relevant to this work, and turn what it finds into the questions you ask next. Interview the user one question at a time, prioritizing questions where the answer would change the architecture, each with your recommended answer so a reply is a yes or a correction. Anything they'd only recognize by seeing, build wildly different directions on the prototyper's row and let them react to the rendering; never describe a look. For behavior nobody can put into words, ask for an implementation that already has it, read it, and reimplement the same semantics here. Told to run autonomously, settle each open question from the repository's precedent first, and where only the standard answer was available, say so in the PR body.

When nothing about the design is open, write a contract of a few lines, turn its criteria into failing tests, and build. When one decision is open, costly to reverse, and settled by no cheap spike, get one blinded draft from a Claude model and one from a GPT model and synthesize the answer yourself. When you can state the whole diff in one sentence, skip straight to build and review. Never skip, at any size: the worktree, the gates green, both critics on the integrated diff, and the PR.

Write the run contract, one working file on the branch, leading with the decisions the user is most likely to change (the data model, the interfaces, anything user-facing), then the slice map with each worker's owned files, the interfaces between slices, and the quality bar the critics score against. Turn every acceptance criterion that can be a test into a failing test now; a failing test turns green through code, never through editing the test. A bar no existing gate checks gets a small reproducible check built first. When the contract fixes decisions worth attacking, one cold read before building: a fresh read-only dispatch on the plan editor's row, given only the contract, the tests, and the repository, returns it approved or rewritten whole; take what survives your own judgment. The contract stays live: when the code moves it moves in the same commit, and anything that forces a deviation takes the conservative option, lands in the contract with its reason, and keeps going. Delete the contract before the PR opens: by then it lives in the tests, the PR body, and, where the repository keeps decision records, one record for what the code cannot explain by itself.

Dispatch one fresh builder per slice on the builder's row, each touching only its owned files, and sequence coupled slices under a single owner; renames, doc sync, and other mechanical chores go to the mechanic's row. Give each builder the contract, the gate commands, and these rules copied in full: work test-first, watching each test fail before writing code; test behavior through public interfaces, never internals; mock only at a system boundary; prefer what the codebase or its dependencies already provide, and give any custom mechanism a reason a reviewer can inspect; aim YAGNI at speculative structure, never at validation, data safety, security, or error handling; match the surrounding code's style; when the code contradicts the brief, or a third attempt fails, stop and ask with evidence instead of pushing through. When a builder shows the brief is wrong, fix the contract before dispatching anything else. Keep the gates green at every integrate, treat every report as a claim to verify against the real code, and when the slices land, dispatch one simplification pass by a builder so review judges the final shape.

/loop the review until nothing blocking survives a full round. Each round, two harsh critics read the integrated diff cold, each a fresh dispatch given the diff, the repository, and the quality bar alone, never the contract: one on the Claude critic's row and one on the GPT critic's row, judging whether the diff reads like the best code already in the repository, with the repository's own review doctrine as the specifics, and flagging anything a reviewer would send back. When the work has a visible reference (a pointed-at implementation, a rendered design), each puts the result beside it, blind, and says which is better and why. Separately each round, one fresh dispatch on the conformance checker's row compares the diff against the contract and the tests, reporting what is missing, what nobody asked for, and what looks wrong, quoting the contract line each finding rests on; neither pass sees the other's findings. Adversarially verify every finding yourself before accepting it. Send accepted blockers (correctness, security, data safety, a broken public interface) to fresh builders and rerun the loop at the new head; file real findings below that bar as followup issues before the PR opens.

Hand the accepted head to a fresh worker on the QA driver's row that saw none of the work: it drives every changed scenario through the interface a real user uses, records evidence per verdict, and never touches product code or product tests. Read each failure yourself first: a failure that traces to a decision in the contract goes back to the contract, never to a builder patching the symptom. Every product fix re-enters the review loop.

Before you open the PR, point at the evidence for every decision and criterion in the contract, a test, a command output, a QA verdict; unproven means not done. Write the PR for a reader who was not in the run: what changed and why, the decisions made on the user's behalf with the one most likely to draw a different answer first, the deviations log, both critics' and the conformance check's verdicts, and the QA evidence linked where the PR can read it. /loop on the checks as tracked background Bash until every one is green and the merge state clean, routing anything a code change can fix back through build, review, and QA. Then report the PR ready and stop; anything only a person can clear, name it to the user and leave the PR open.
