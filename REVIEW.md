# Reviewing bottega

Bottega is a method in markdown; most defects are false claims, drifted duplicates, and register violations, not crashing code.

- Worker models are named where the dispatch happens: `skills/maestro` states the orchestrator model and its workers' models in the sentences that dispatch them, the panel's seats are named in `skills/panel`, and the review engines in `skills/autoreview/SKILL.md`. A second home for any of these is a defect, and so is a caller restating a callee's facts instead of carrying the invocation.
- Enforcement lives in `hooks/route-guard.mjs`, which states its own policy; review a guard change against that file and `tests/route-guard.test.ts`, and treat any prose restating the guard's policy as a drifted duplicate.
- No agent identity file exists. Worker method arrives per dispatch from skills (`implement`, `qa`).
- The skills tree is the product and must stay harness-portable: nothing in `skills/` may assume slash commands, subagents, or a plugin root exists, except where a harness is named.
- The same tree must stay self-contained: nothing in `skills/` references this repository's own record (`docs/`, `REVIEW.md`, `tests/`), which does not install with the plugin. A path a skill names either resolves inside `skills/`, names a component the plugin ships, or names a file of the host repository the run works on.
- The codex reads dispatch through `bottega:use-codex`: a sonnet subagent forwards one `codex-task task` command, and the wrapper itself refuses a task missing `--model` or `--effort`; the review engines are fresh CLI contexts. The guard inspects unpinned `codex-task task` and `codex exec` commands. The panel's claude seat and its judge are subagents, so the guard does read them, and they pass by naming opus-5.
- Reviewing this repo's prose means judging the diff as skill writing: held to the skill-writing doctrine (leading words, no-ops, duplication, sediment), the register, consistency of the map and cross-references, and the logical flow of the method (every route names an action that resolves; every term has one definition). A read of the same diff by another company's model is welcome; the autoreview engine is not the tool for prose, by its own contract. On a host repo, a run's Review phase dispatches a fresh seat that runs the vendored method whole: single-engine by default, both engines when the maestro's dispatch set the panel, and Claude workers taking the GPT reads with the gap recorded when the codex CLI is absent.
- Every claim in AGENTS.md, README.md, and skill cross-references must be true of the tree in the same diff that changes the tree.
- Register: plain engineering English, no em dashes, no semicolons in skills prose, no "bearing"/"bears on"/"ledger", one route verb ("use"). A skill's body talks to the agent doing the work, imperative, per `skills-internal/write-bottega-skills`.
- Over-specification is a defect: a worker instruction that scripts what a frontier model does unprompted, enumerates cases one stated principle covers, or steers by always/never where the reason would do. The quantifiers the doctrine tests pin are acceptance bars, not this defect.
- `docs/lessons/` carries the repository's failure records. Two carry review checks, and a violation of either is a finding: a capability the diff adopts ships either its working verification or a tracking issue (neither present is the finding), and a delivered design does not contradict what its own reading concluded, stated in the spec or the ADR that carries the decision.
- This file and the skill-writing checklist are the whole rubric, and it is closed: a lens not listed here is not applied. A skill that passes is reopened only for a failure observed in a run or a change the owner asks for; a re-read that would merely improve the text is not a finding.
