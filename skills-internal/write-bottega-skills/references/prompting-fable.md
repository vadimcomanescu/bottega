# Prompting Claude Fable 5

Source: Prompting Claude Fable 5, Anthropic platform documentation (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5). A distillation for the skill writer: reread the source when the model generation moves.

The teams seeing the best outcomes point this generation at their hardest unsolved problems: pick a task harder than you would hand a prior model, end-to-end work that takes a person hours, days, or weeks, and have the model scope it, ask clarifying questions, and execute. The capability jump is itself the prompt to re-evaluate which instructions, tools, and guardrails are still needed. Skills developed for prior models are often too prescriptive for it and can degrade output: review them and consider removing older instructions where default performance is better. It also updates skills well on the fly from what a task teaches it.

What moved against the prior generation: multiday goal-directed runs with strong instruction retention, first-shot correctness on complex well-specified problems, noticeably higher bug-finding recall including search across a codebase and its repository history, substantially more accurate reading of dense technical images and screenshots (often with fewer output tokens, using bash and crop tools on flipped, blurry, or noisy images), reliable next-step judgment on ambiguous multithreaded requests, and dependable dispatch of parallel subagents with ongoing communication to long-running subagents and peer agents. Turns run longer by default, minutes at higher effort and hours on autonomous runs, so adjust timeouts and check on runs asynchronously rather than blocking.

Instruction following is strong enough that a brief instruction steers most behaviors, with no need to enumerate each behavior by name. Un-steered at higher effort the model elaborates: it surveys options it will not pursue, explains root causes at length, produces heavily structured PR descriptions, and writes comments narrating the next line. One short brevity instruction is as effective as listing every pattern. The steers the page ships, each a short block to paste:

- Act on enough information: do not re-derive established facts, re-litigate decided questions, or narrate options you will not pursue. Weighing a choice, give a recommendation, not a survey.
- Brevity: lead with the outcome, the sentence answering what happened or what was found. Keep output short by dropping details that do not change what the reader does next, never by compressing into fragments, arrow chains, or jargon, because readability matters more than concision.
- Summaries after long runs: terse shorthand between tool calls is fine, that is the model thinking out loud, but the final message after unwatched work is the reader's first look at any of it. Re-ground rather than continue the working thread: complete sentences, none of the shorthand or invented labels built up along the way, every file, commit, or flag in its own plain-language clause, and the one or two things needed from the reader each explained as new.
- Scope: no features, refactors, or abstractions beyond what the task requires, the simplest thing that works well, validation only at system boundaries, trust in internal code and framework guarantees, and no compatibility shims or feature flags where the code can simply change.
- Grounded progress: before reporting progress, audit each claim against a tool result from the session, and say explicitly what is not yet verified. Report outcomes faithfully: failing tests with their output, skipped steps named as skipped, verified work stated plainly without hedging. In Anthropic's testing the audit instruction nearly eliminated fabricated status reports.
- Boundaries: when the user is describing a problem rather than requesting a change, the deliverable is the assessment. Before a state-changing command, check the evidence supports that specific action, because a signal that pattern-matches a known failure may have a different cause.
- Checkpoints: pause only for a destructive or irreversible action, a real scope change, or input only the user can provide, and ask rather than ending the turn on a promise.
- Autonomy: for pipelines, state that the user is not watching and that reversible actions that follow from the original request proceed without asking, because deep in a long session the model can end a turn on a statement of intent instead of the tool call. A plain continue recovers it.
- Memory: give the model a place to record lessons, one per file with a one-line summary, corrections and confirmed approaches alike with why they mattered, updated rather than duplicated, deleted when wrong, and nothing saved that the repo or the chat history already records. Bootstrap the store by having the model review past sessions with subagents and record the themes.
- Delegation: use subagents frequently, with explicit guidance on when delegation is appropriate. Delegate independent subtasks and keep working while they run, intervening when one goes off track. Prefer asynchronous communication over blocking on each return, and keep long-lived subagents whose retained context saves cost through cache reads and avoids bottlenecking on the slowest one.
- Reason with the request: say what the larger task is, who it is for, and what the output enables, so the model connects the task to relevant information instead of inferring intent.

Scaffolding notes: separate fresh-context verifier subagents tend to outperform self-critique on long runs, so have a long run establish its own checking method and run it at a stated interval, verifying against the specification with subagents. Prompts, skills, or harness instructions that tell the model to echo, transcribe, or explain its internal reasoning as response text can trigger refusals on this generation, so read the structured thinking output instead, and audit migrated skills and system prompts for reflection or show-your-thinking instructions. A send-to-user tool rarely gets called without elicitation language in the system prompt, carries only content the user must read verbatim, never narration, and an agent that only narrates routine progress does not need one. Avoid surfacing context-budget countdowns, which prompt the model to wrap up early, and where one must be shown, pair it with a reassurance that ample context remains.

Effort is the primary control over intelligence, latency, and cost: high as the default, xhigh for the most capability-sensitive work, medium or low for routine work, which still often beats a prior generation's xhigh. Higher effort buys the most rigorous verification and reasoning, and it is also where the elaboration failures live: on routine work the model gathers context and deliberates past what the task needs, and the scope steer above exists for the tidying it otherwise adds. Reduce effort when a task completes correctly but takes longer than it should, or when you want a quicker, more interactive working style.
