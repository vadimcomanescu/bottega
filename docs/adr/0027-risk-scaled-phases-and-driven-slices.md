# Phases scale by risk, slices are driven as they land, and the register of flows is executable

Three lab runs on a real repository (a micro task, a small risky bug fix, and a full feature) tested the method's routing and its QA loop, and each returned the same class of result: the cheap signal the method was reading is not the signal that predicts cost. The last decision below rests on a reading of outside practice rather than a lab run and lands in the same place: the register QA was scoped from was a prose document, and prose describing code stops being true.

**The delivery call reads risk, not sentence length.** Until now a run took no spec and no plan when the orchestrator could state its whole diff in one sentence. The small bug fix passed that test and still went wrong: both fix candidates named in the issue were wrong under a constraint the module carried, and only writing the fixed decisions down caught it, before any code was written. Sentence length measures how easy the work is to describe, not what a wrong call costs to undo. So a phase now runs where discovery left an unknown unresolved or where a wrong call would be costly to reverse, and settled discovery shrinks spec and plan to what stays open: a paragraph of fixed decisions where the work is small and mistakes are expensive, neither document where nothing is open and reversal is cheap. The cost of this is real: judging reversal cost is a judgment call where sentence length was a mechanical one, and the orchestrator can now under-call a risky change. The provisional-both-ways rule is what limits that, and it stays.

**A slice that changes a user-facing surface is driven as soon as it lands on the run branch.** Review reads a diff and QA drives the accepted head, and between them sat every defect that only shows up in a running interface at a moment no test reproduces. In the lab a slice drive caught a defect in which an action rendered as available when it was not yet eligible, before review ever read the diff, and the driver's freedom to report what it crossed outside its named scenarios turned up a defect in the window before the page finished hydrating that both the code review and the scripted end-to-end suite missed, because scripted clicks trust the page. The alternative considered was leaving all driving in the QA phase, which is cheaper per run but pays for every miss with a full review, acceptance, and QA cycle after integration. The cost accepted is one driver dispatch per user-facing slice.

The drive sits after the merge, not before it. Driving the builder's worktree before integration was the first shape of this rule, and it verified a state the run never keeps: the worktree is one slice deep, so no drive can show one slice interacting with another, and everything the run does next (the merge, the slices after it, the simplification pass) changes the code the verdict was given on. Driving the run branch once the slice has merged, and before the run proceeds past it, puts every verdict on the integrated state the run carries forward. What still changes under it is the simplification pass, which preserves behavior and re-runs the gates, and the QA phase drives the final accepted head.

**A driver completes its scenarios and reports the divergences in one batch.** The rule it replaces stopped the drive on the first divergence so the orchestrator could classify before more driving happened. What that bought (a classification that is never stale) is worth less than what it costs: N divergences became N sequential repair cycles, where batching cleared the same set in one. Stopping early is now reserved for a divergence that leaves the remaining scenarios undrivable, which is the only case where continuing produces nothing.

**The register of must-not-break flows is the end-to-end suite, and QA's scope is derived per run.** Setup used to draft a critical-journeys doc, one journey per user-visible capability, and the QA phase scoped its drive from that doc where a repo kept one (adopted in `docs/adr/0012-harness-engineering-adoption.md`, whose item this supersedes). The reading behind the change: the critical-user-journey practice it borrowed from produces a monitoring specification, not a repo doc that tests or reviewers read; the one source scoping tests from such a list is a defensive publication with no evaluation behind it; and BDD already ran the experiment of keeping the flows as maintained text and abandoned it on maintenance cost. Prose describing current code behavior is also the artifact class that measurably rots. Setup now verifies that each must-not-break flow is exercised by an end-to-end check the suite can run and name on its own, drafts the missing specs where a user-facing surface has none, and files one issue naming the uncovered flows where the harness cannot run the suite. QA's scope comes from the agreed spec's behaviors, the diff, and that tagged suite. The cost accepted is that a repo with no runnable end-to-end suite gets an issue instead of a document, which is a slower path to coverage and an honest one.

**Dynamic workflows are opted in for a run's fan-out phases**, rather than weighed per phase. A four-explorer workflow produced the grounding every later phase stood on, and the route guard held the invariant that made the standing grant safe: it passed the workflows whose `agent()` calls named a worker's model and denied the unpinned and the Fable-routed ones. The opt-in is a standing grant because the guard, not the orchestrator's attention, is what enforces the model on each call.
