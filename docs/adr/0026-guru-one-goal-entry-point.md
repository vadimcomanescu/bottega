# Guru: the whole method as one prompt, the agreement in a contract that never merges

`/bottega:guru` is a second entry point beside maestro, and its body is the entire method as one standalone prompt: one goal, a hard done bar, and no phase machinery. It uses no other skill except `bottega:panel` for a costly open decision, and it names its workers' models where it dispatches them rather than reading the worker table, because a prompt that stands alone cannot resolve a row. That makes it the fourth file allowed to name a model, recorded in the doctrine test beside the table, maestro's orchestrator sentence, the panel's seats, and the vendored engine. The delivery bar is unchanged and never moves: the run's own worktree and branch, gates green at the delivered head, a Claude and a codex critic on the integrated diff, evidence behind every requirement, and a PR that lands as `docs/adr/0028-the-launch-decides-the-release.md` decides.

What changes is the paper and the shape. The agreement lives in a run contract, one working file on the branch carrying the decisions the user is most likely to change first, then the slices with their owned files, each specified by the richest artifact that exists for it: an implementation to port, a render the user reacted to, a failing test where one pins a criterion, prose only where no artifact can stand in. The contract is scaled by what is unknown and what is costly to reverse, never by the size of the diff. It moves in the same commits as the code and is deleted before the PR opens, by which time the PR body carries its decisions and at most one decision record survives it.

ADR 0007 stands for maestro runs: a spec the user agrees to is a file with its own status line, committed and merged with the code it describes. Guru is the parallel posture, chosen by the user at invocation, and the two entry points coexist until run evidence decides between them.

Grounds, from outside practice: the recurring field finding through 2026 is that a committed spec or plan fails by staleness, not by storage. Practitioners report plan files drifting into fiction the agent still trusts within a sprint, and the records that hold up are the test suite, the PR description, and decision records: Canciani throws the plan away and keeps only ADRs, Brody keeps plans in scratch and folds a condensed copy into the PR body, Eisele gives specs an expiration date and lets their content decay into the codebase, and the specification-by-example camp replaces prose with executable examples. The counter-camp (Osmani, Kiro, and practitioners holding agents on course with a plan file) commits the file for drift control during the run, which is why the contract exists on the branch while the run lives and only its merge is dropped. A measured one-prompt build (Shumer's Claude of Duty) kept a single contract file as the workers' only coordination mechanism, scored adversarial critics against a written bar with a blind side-by-side against the real benchmark, and found one sequential owner per coupled concern cutting defects where parallel fan-out raised them. Anthropic's Claude 5 context-engineering guidance grounds a narrower part of the design: an existing test suite or reference implementation serves as a richer spec than a markdown description, so the contract hands workers artifacts over prose; rubrics belong with verifier agents in dynamic workflows; and prompts state goals over steps rather than over-constraining a frontier model.

Two instructions exist because this model generation under-reaches without them, not because a competent engineer would forget them. Anthropic's own migration guidance for the tier guru runs on records that search and knowledge retrieval trigger less often once a system prompt is present, and that capabilities needing an explicit decide-to-use step (subagents, memory, custom tools, installed skills) are reached for conservatively; the prescribed remedy in both cases is explicit triggering. So guru names the outward sweep (how others already solved this, and what the installed version actually does, read from its own docs and source rather than from memory) and tells each builder to follow the technology skills installed in the runtime and the current documentation for the installed version. Without the first, every decision the repository does not settle comes from the model's priors, which is the field guide's unknown-known failure and, for version-sensitive facts, a prior frozen at training cutoff. Without the second, progressive disclosure never fires: the runtime's skills load only when something reaches for them.

Grounds, from bottega's own lab (three experiments on a real portal, ~3M worker tokens, `throwaway/bottega-lab`): the cold read of the plan by a codex editor under an approve-or-rewrite-whole contract was the cheapest defect prevention measured, catching four real design defects before any code ran, so the prompt keeps that contract and not a softer read. A critic drive with license to roam past the changed scenarios caught defects no scenario checklist and no end-to-end suite reached, including a hydration window that swallowed the first press of every control, which is why the drive lands per user-facing slice before merge and the terminal pass shrinks to a thin sweep. A review brief that asks only for findings returned two lines off 144k tokens of real work; adding what the reviewer verified and found sound to the brief fixed it. Cross-model contradictions appeared in every experiment and each needed a reasoned orchestrator call, so arbitration is stated. A repair commit asserted a fix the re-drive then disproved, so a repair is done only when the re-drive confirms it. A lean brief that dropped the docs-inside-the-slice duty cost an extra dispatch, so that duty is named in the builder brief. The explore fan-out produced the file and line evidence every later phase stood on, and one of its four reports recovered undocumented mechanics of an installed library that no model holds in its priors, which is the sweep the grounding paragraph now names. A builder that found its brief's premise false took the conservative call and reported it with evidence, which the lab flagged as a doctrine question: guru answers it as deviate-and-report, asking only when the answer would cross the slice.
