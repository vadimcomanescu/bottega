# Guru: the whole method as one prompt, the agreement in a contract that never merges

`/bottega:guru` is a second entry point beside maestro, and its body is the entire method as one goal-driven prompt: one goal, a hard done bar, and the bottega skills (discover, open, build, implementing, panel, qa) as building blocks rather than phases to walk, with the worker table carrying every dispatch's model and effort and the codex dispatch method carrying GPT mechanics. It stands beside maestro with no dependency on it. The delivery bar itself is unchanged and never moves: the run's own worktree and branch, gates green at the delivered head, a Claude and a GPT reading the integrated diff, QA evidence, and a PR the owner merges.

What changes is the paper and the shape. The agreement lives in a run contract, one working file on the branch carrying the settled decisions, the slices, the quality bar, and the deviations log, plus a failing test for every criterion a test can check. The contract moves in the same commits as the code and never merges: by close its content is the tests, the PR body, and at most one decision record. The run is orchestrated ultracode, every fan-out a dynamic workflow, and the review is a loop of two blind critics seated on new rows of the worker table beside the conformance checker's row, in place of the vendored engine. Every stage before build is bought per open decision rather than walked as a phase.

ADR 0007 stands for maestro runs: a spec the user agrees to is a file with its own status line, committed and merged with the code it describes. Guru is the parallel posture, chosen by the user at invocation, and the two entry points coexist until run evidence decides between them.

Grounds: the recurring field finding through 2026 is that a committed spec or plan fails by staleness, not by storage. Practitioners report plan files drifting into fiction the agent still trusts within a sprint, and the records that hold up are the test suite, the PR description, and decision records: Canciani throws the plan away and keeps only ADRs, Brody keeps plans in scratch and folds a condensed copy into the PR body, Eisele gives specs an expiration date and lets their content decay into the codebase, and the tests-as-spec camp runs from Marcano's specification by example to Willison's test-first agent guidance. The counter-camp (Osmani, Kiro, and practitioners holding agents on course with a plan file) commits the file for drift control during the run, which is why the contract exists on the branch while the run lives and only its merge is dropped. A measured one-prompt build (Shumer's Claude of Duty) kept a single contract file as the workers' only coordination mechanism, scored adversarial critics against a written bar with a blind side-by-side against the real benchmark, and found one sequential owner per coupled concern cutting defects where parallel fan-out raised them. Anthropic's Claude 5 context-engineering guidance points the same way: a spec may be a test suite or a reference implementation rather than markdown, rubrics belong with verifier agents in dynamic workflows, and prompts state goals over steps.
