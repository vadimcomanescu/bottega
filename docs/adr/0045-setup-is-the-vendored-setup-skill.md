# 0045: Setup is the vendored setup skill plus the labels and the claim

Superseded on 2026-08-07 by `0046-beads-is-the-tracker.md`: setup is bottega's own forked skill again, the tracker is beads and no longer pluggable, and the two remote tracker templates are deleted. What survives is this record's reasoning for what setup owns — the one-time tracker configuration, the labels created on the remote, and the atomic branch claim — and the five-role triage vocabulary it adopted.

Decision. `/bottega:setup` is the vendored setup skill from `mattpocock/skills` (`THIRD_PARTY.md` records the pin), run once per repository: it settles the issue tracker, the triage label vocabulary, and the domain doc layout, one section at a time with a recommended answer first. Bottega adds two mechanics and nothing else: the labels named in `triage-labels.md` are created on the remote with get-or-create rather than only written into a file, and the remote tracker templates carry an atomic branch claim (create the issue's branch with a force-with-lease empty expected value, so exactly one creation wins and assignment stays the human-visible signal). Adopting the skill adopts the five-role triage vocabulary into bottega-managed repos: `ready-for-agent` marks an issue that is fully specified, which is what a launch takes as input.

Why. The house setup skill through 0.181.0 reconciled a machine and repository in five steps, and each step duplicated a check the run performs at the moment it matters: `bottega:open` confirms the codex login per-run and discovers, verifies, and writes back the project's commands and the landing procedure, `bottega:close` creates the `hold` label it brakes with, maestro replaces unavailable codex with Opus at the same reasoning level, the review's secret preflight fails immediately naming its install link, and a timed-out codex watch is rerun because the job lives on disk. A verification made in a setup session is unreadable to the next session, so those steps bought nothing the repository could keep, and machines that never ran setup completed runs without it. What setup genuinely owns is the part no run heals: the one-time tracker configuration, the label vocabulary existing on the remote before `/triage` applies it, and the claim convention that makes two sessions taking work from one tracker safe.

Trade-off. The skill's prose is upstream's, so its register and structure follow that author and a sync is a re-copy plus the recorded local edits, not a house rewrite. The five triage states live in the vendored files and not in `CONTEXT.md`: no run skill writes them yet, and giving them glossary entries waits until one does.
