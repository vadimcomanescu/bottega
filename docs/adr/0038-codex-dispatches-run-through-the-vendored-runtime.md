# Codex dispatches run through the vendored companion runtime

Date: 2026-07-29.

Every codex dispatch was a raw `codex exec` the orchestrator held open as tracked background Bash for the whole run, and four costs came with that shape. A dispatch occupied a shell call from launch to exit, so the orchestrator's own turn carried the run. Recovery needed a session id scraped out of the log with `grep -m1 "session id:"`, and the resume then had to re-pin the model, effort, and sandbox by hand, because a bare resume ran at the host config's values: measured on a session pinned to `low` and `read-only`, it came back at `xhigh` and `danger-full-access`. Liveness was a read of the log file's age, which cannot tell a run thinking from a run hung. An interrupted session left the codex process orphaned, with the finished report sitting unread in an out file (`docs/lessons/no-subagent-holds-a-long-dispatch.md`, `docs/lessons/subagent-background-work-dies-silently.md`).

Decision: codex dispatches run through OpenAI's codex plugin for Claude Code, vendored verbatim plus two documented hunks and recorded in `THIRD_PARTY.md`. A dispatch is the `bottega:codex-rescue` subagent (model sonnet, matching the vendored agent frontmatter) carrying the brief and explicit `--model` and `--effort` pins, forwarding once to `node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs" task` and returning its stdout verbatim. Long work adds `--background`, so the subagent returns a job receipt in seconds and the orchestrator watches from its own turn with one tracked `status <job-id> --wait --timeout-ms <ms>`, whose completion re-invokes it. Job state and threads persist on disk per workspace, so a cut-short watch reruns `status --wait`, a follow-up or repair on the same job continues with `task --resume-last`, and `cancel <job-id>` kills a run judged stalled. The SessionEnd hook tears down the broker and the session's jobs.

This supersedes ADR 0022, whose method was bottega's own prose driving raw `codex exec`. What 0022 rejected still holds and is why this vendoring works where the last one did not: it took a document that mixed its author's work routing and model defaults into the mechanics, and this runtime is mechanics with no routing in it, so every dispatch site still names its own model and effort (ADR 0018). What ADR 0020 settled survives in the part that matters: the call that can run for tens of minutes is still the orchestrator's own tracked background Bash, and the subagent now holds nothing longer than a routine command, which is what the two lessons above demanded and instruction text never delivered.

Consequences worth naming. The runtime is under the `THIRD_PARTY.md` sync contract: scripts re-copied byte-identical with two recorded hunks, the agent and its two preloaded skills carrying recorded scoping edits (namespace, `--background` and `--cwd` forwarding, the effort list), never edited beyond that record. One agent definition now exists in this repo, `agents/codex-rescue.md`, and it is vendored, so its "You are" opening and its prose are upstream's apart from that record. The forwarder subagent runs on sonnet, the model its vendored frontmatter names, which narrows ADR 0018's "sonnet leaves the system": sonnet holds exactly one seat, a forwarder that makes one Bash call and no judgment, and every dispatch still names it explicitly. The route guard reads the new dispatch shape at two layers: the subagent dispatch, where it verifiably sees the owner's session, and the forwarded `codex-companion.mjs task` command, denied when unpinned, though whether that inner event carries the owner's session id is undocumented, filed as followup #180. The stop-review-gate hook stays unregistered: its script is vendored for sync simplicity, and bottega's review gate is the code-review skill. The script runs codex read-only until `--write` is passed, but the rescue agent adds `--write` unless the dispatch asks for read-only, so a cross-read says so or comes back able to edit the tree. There is no `--ignore-user-config` and no sandbox flag in this runtime, so the app-server reads the machine's codex config, which is also where web search comes from: no per-dispatch flag turns it on, a brief asks for web grounding and gets it when the machine's config serves it. A machine carrying the upstream codex plugin beside bottega runs both SessionStart hooks, the last writer decides the shared state root, and the two identical runtimes then share one broker and one job list, which the runs recorded below showed and is accepted.

Verified live before this record landed, on codex-cli 0.144.0: `setup --json` reported the CLI authenticated, a foreground `task` returned its report, `--resume-last` continued the thread with its memory intact, a `--background` dispatch returned a `task-<id>` receipt in seconds, one `status <id> --wait` held until the job finished, `result <id>` returned the exact hash the brief asked for, `cancel` killed a running job, and an effort the model's API does not serve failed the job at start with the API's error in the receipt. The runs were made on a machine carrying the upstream codex plugin beside bottega, and the runtime reused that plugin's broker and state root as one shared runtime.
