# 0028: The launch decides the release

Date: 2026-07-27

Supersedes 0024's release clause and the clause of 0026's delivery bar that names the owner's merge. Verification is untouched: the integrated cross-family review, QA, and the project's checks remain the whole bar, and a run still never merges a PR by hand and never approves one. What moves is where the owner's release authority is exercised. Under 0024 it sat at a merge click after close reported ready, and on every green PR that click confirmed what the recorded evidence already showed while the work waited on a person. The owner moved the decision to the launch: a request either says the PR lands on green or says it holds, and when it says neither, maestro asks the user one plain question, land on green or hold for you, before any PR can exist. The answer is recorded with the run's state and close carries it to the PR.

Which machinery lands a PR is the host repository's decision, held in that repository's own documented procedure, and a run reads it rather than carrying a copy. What the run depends on is two facts: a brake, a hold label enforced by its own required check, the same shape as Prow's do-not-merge/hold (https://github.com/kubernetes-sigs/prow/blob/main/pkg/plugins/hold/hold.go), where the label blocks and its absence never authorizes; and a way to land a green PR without a person. GitHub's merge queue, the platform's own mechanism for that, was checked and needs an organization-owned public repository or GitHub Enterprise Cloud (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue), so auto-merge behind required checks stands in for it.

Arming that auto-merge is the run's own act wherever the repository makes arming the opener's act, because the run is the account that opens the PR, and a merge made with `GITHUB_TOKEN` starts no workflow run on the default branch (https://docs.github.com/en/actions/concepts/security/github_token), so nothing is gained by a workflow or a long-lived token holding merge rights and a token the owner must mint by hand is one more thing waiting on a person. Arming is not authorizing: the required checks and the hold label decide whether an armed PR lands, so the run's part is the release answer, the label on a held PR's create call with a required check confirmed to enforce it, the arm, and the watch to completion. A PR the auto-merge lands during that watch is reported merged with its head SHA and evidence, and the run's working state is swept in that same session. Saying hold at launch, or adding the label while the PR is open, is the human act; removing the label lands it.

Corrected the same day this record was written: arming was first put on the host repository's own workflow holding a fine-grained PAT, and the strict-policy and post-merge-risk reasoning of whichever repository adopts this was restated here. Both are struck. A secret the owner mints by hand is the waiting-on-a-person this decision removes, and another repository's ruleset reasoning is that repository's to state.
