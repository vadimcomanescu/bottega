# Mid-run questions the repo can answer are decided, not asked

The 2026-07-29 run for nadicodeai #609/#610/#612 asked the owner five questions. One was the launch's standing release question. Of the other four, three were answerable from the repo's own words: the recurrence semantics the issue text states outright, the parser unification whose stated goal decides the scope, and a builder's four newly found duplicate parsers that the same goal covers. The fourth, breaking a written expand/contract MUST in the host repo's operations doc, was a real owner question, but it had an obvious provisional path: obey the doc. Every question was a blocking prompt, so an absent owner would have stalled the run four times. The orchestrator was capable of every one of these decisions and had the evidence in hand. What it lacked was a sentence saying deciding is its job.

Decision. Maestro decides and keeps moving wherever the repo can answer the question: the issue's words, the docs' rules, discovery's record, cheap reversal. Each call is said in the conversation and in the PR with its reason, for the owner to overrule. Questions go to the owner only when nothing in the repo can answer them: breaking a rule the repo wrote down, a trade-off only the owner can weigh, a step that cannot be undone. A question never parks the run: the safest answer the repo supports proceeds as provisional while unblocked work continues.

The boundary against the same day's opposite failure (ADR 0035): the review phase's brakes stand untouched. A finding whose fix changes what the work promises, and two unconverged fix cycles, still stop at the owner, because there the evidence showed the orchestrator deciding alone is what burned. The line between the two is where the answer lives: mid-run discoveries whose answer sits in the repo are the orchestrator's, contract changes and rule exceptions whose answer sits in the owner's head are not.

The trade-off booked honestly: maestro will sometimes decide something the owner wanted to weigh, and on a land-on-green run that call can merge before the owner reads it. Counterweights: the call and its reason are in the conversation and the PR the moment they are made, the launch's own answer chose land-on-green, and a wrong scope call is a revert, not a migration.
