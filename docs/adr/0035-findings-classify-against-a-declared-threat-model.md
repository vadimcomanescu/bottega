# Review findings classify against a declared threat model

The 2026-07-28 run for nadicodeai #623 (bottega issue #172) showed the review loop's classification missing one axis. A hygiene check gained symlink-containment armor across five review cycles, 863 lines defending against layouts only a person could construct, because every finding was real, reproducible, and introduced by the diff, so every finding legitimately classified as an in-scope blocker and the two-cycle pause had no vocabulary with which to say no. The scope contract's own words ("reject unrealistic edge cases, speculative risks") lost every round, because a constructed repro defeats the speculative label, and an unpinned check reads under the reviewer's always-on security perspective as a sandbox boundary, making every bypass a concrete security exposure, the one exception that authorizes blowing up scope.

Decision. The scope baseline frozen before the first review carries one sentence of threat model: the class of input the changed code answers for (accidental states, adversarial input, untrusted data). That sentence travels in the review prompt as fixed material beside `REVIEW.md` and the smell baseline, while the rest of the run's design stays out of the prompt, so reviewer isolation is preserved. The finding classification gains a fourth class, out of threat model: real, reproducible, and still not work, because its failure scenario requires an actor the code does not answer for. The maestro rules on every finding before any fix dispatch, rejects out-of-model findings by rule with the rejection recorded in the review evidence, computes the diff-growth numbers against the frozen baseline before each dispatch instead of judging by feel, and continues past the two-cycle pause only when the cycle series is narrowing. In maestro, work that adds a check, gate, or validator writes its threat model in the design and ships it with the check, and a second-opinion revision that adds a requirement reaches the owner before any builder.

The trade-off booked honestly: a wrong or too-narrow threat model now hides a real exposure behind a by-rule rejection. Two counterweights: the model is one owner-visible sentence in the design and in the shipped check, so it is one sentence to widen, and every by-rule rejection is recorded in the review evidence, so a wrong model is visible in the PR rather than silent.

This changes no engine mechanics and adds no phase to the run. The vendored review document's local scoping is recorded in `THIRD_PARTY.md` as with every prior weave. ADR 0033's one simple flow stands.
